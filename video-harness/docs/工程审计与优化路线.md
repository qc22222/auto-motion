# 视频流水线工程审计与优化路线

## 结论

现有一次性 `auto-motion` 黑箱的价值在于：按镜头把完整语义交给 Claude Code，由它自行查资料、选视觉概念、写 HyperFrames 代码并渲染。这个创作内核应保留。

需要优化的是外围确定性系统：把确认文案、真实 TTS、字词时间戳、分镜时长、字幕、场景状态、审阅和交付连接为同一条可恢复流水线；不要用固定模板替换场景创作，也不要让前端重新实现状态机。

## 第一性原理约束

1. **唯一事实来源是确认文案**：配音、字幕文字和镜头语义都从同一份文案派生，ASR/SRT 只作为时间轴产物或旧项目导入格式。
2. **真实音频决定时间**：场景时长、字幕时间和最终视频长度必须由真实 TTS 及显式停留时间共同决定。
3. **生成模型只负责非确定性创作**：视觉概念和动画代码交给现有黑箱；状态、路径、时长、缓存、审批和验收由 Harness 负责。
4. **每个阶段都能恢复**：失败后从失效的最小场景或阶段继续，不依赖操作者记住上一条命令。
5. **测试产物不能冒充生产产物**：模拟静音、桩引擎和占位动画必须显式标记，生产校验默认拒绝。

## 必须保留

- 原 `auto-motion` 的逐镜头语义拆分和顺序执行方式。
- Claude Code 对单场景视觉概念、素材选择、MG 动效和代码实现的自主空间。
- 项目本地 HyperFrames 技能、安全入口、缓存和中文路径兼容规则。
- 每个镜头独立目录、独立日志、独立 MP4 和失败后可单独重试的结构。
- FFmpeg 最终拼接与媒体规格验收。

## 本轮已完成

- 修复真实 TTS 旁白未包含 `extraHold`/无旁白区段的问题；现在完整音轨会按 Storyboard 顺序补静音并验证总时长。
- 修复场景 `PROMPT.md` 指向 BRIEF、设计、Storyboard 和场景 JSON 的错误相对路径。
- 新增 `generate` 场景生成桥接：按顺序调用可替换 runner，默认 runner 保留 Claude Code + HyperFrames 黑箱创作方式，并记录独立日志。
- 新增 `advance` 可恢复流水线：自动推进确定性阶段，只在 `script`、`storyboard`、`review` 三个质量门暂停。
- 生产校验和生产交付默认拒绝模拟音频。
- 审批不能再绕过尚未到达的质量门。
- 场景渲染记录源文件哈希；多个场景过期时只重渲染一个，不会因其他旧 MP4 仍存在而误报全局完成。
- 真实 TTS 返回的每段音频现在必须存在、可探测、时长与元数据一致，并包含有序且不越界的字词时间戳；缺失时间戳会明确失败。
- 新增 8 类分环节修改契约、字段校验、影响预览、过期预览拒绝和精准局部失效，不再依赖通用 JSON 编辑器。
- 新增 `serve` 本地修改工作台：只绑定回环地址，审阅页可进入旁白、音色、分镜、设计、单镜头、字幕和交付修改。
- 新增生产音频提供方级预检：HeyGen 检查本地凭据和授权音色，ElevenLabs/Kokoro 额外检查字词对齐能力，Kokoro 检查依赖、预置音色与非克隆约束。
- 修复 Kokoro 的 BCP-47 语言码和语速传递；非英语 HeyGen 不再误选英语默认音色。
- BGM 异步任务现在必须等待 ready 并验证媒体文件；超时、失败或仍为 pending 时，音频阶段与最终装配都会阻止伪完成。
- 本地服务已接入 `advance`、三个质量门审批、单镜头生成和局部意见；长任务返回可轮询 job，同一项目执行期间拒绝其他写操作，请求不能注入任意执行器或 mock 参数。
- 工作台已显示流水线阶段、当前质量门、单镜头生成/返工、局部意见和音频生产预检，同时继续保留字段级“影响预览 → 确认应用”。
- 自动测试增至 28 项，覆盖真实音频适配、生产预检、BGM 等待、修改矩阵、控制任务、同源服务保护、停留时间、生成桥接、断点续接、审批门、渲染新鲜度和最终交付。

## 当前真实进度

- Harness 的模拟端到端、生成器适配契约和 `advance` 断点续接已经自动验证。
- 现有演示 `runs/video-harness-workflow-demo-20260802` 的音频是 `mock: true` 静音，不能作为真实 TTS 验收证据。
- 现有 Harness 演示场景采用通用占位视觉，不能作为“保留原黑箱效果”的质量基线；质量基线应使用原 `auto-motion` 成片和后续真实 runner 样片。
- 默认 Claude runner 的命令、参数和本机原生 CLI 已检查，但本轮没有发起付费/长时真实场景生成。
- OpenDesign 仍是硬编码静态原型；Harness 自带修改工作台已使用真实项目数据和 API，但尚未嵌入 OpenDesign 三页面。

## 仍需解决的问题

### P0：生产闭环验收

- 提供本人或已授权的真实克隆音色 `voiceId` 与项目本地凭据。
- 用真实 TTS 跑通一条旁白，验证服务商返回/对齐出的字词时间戳、停顿、多音字、英文和数字读法。
- 使用默认黑箱 runner 生成至少一个真实场景，并与原 `auto-motion` 质量基线目视对比。
- 完成一次真实 `advance → 三次批准 → 最终交付`。

### P1：TTS 控制能力

- `direction`、逐段 `delivery`、`settings`、`pronunciations` 已进入项目协议，但当前共享音频引擎实际主要消费文本、语言、语速、provider 和 voiceId；高级控制不能宣称已生效。
- 当前修改一段文案会重新生成全部旁白，尚未实现按段内容哈希缓存和单段试听/重生成。
- 真实音频时间戳的结构、顺序和边界校验已完成；仍需用真实服务商响应完成生产样本验收。

### P1：前端联动

- Harness 自带工作台已接入 `advance`、`approve`、`comment` 和单场景 `generate`，并使用可轮询 job 与单写入互斥；尚未实现真正的子进程取消、事件流和显式重试。
- OpenDesign 必须删除硬编码阶段与字幕数据，并明显区分模拟/真实音频。
- OpenDesign 应迁移到现有薄服务协议；不能让浏览器直接持有 TTS、Claude、HyperFrames 或 FFmpeg 的业务逻辑。

### P2：兼容与成本优化

- 为已有 SRT 黑箱项目提供一次性导入/迁移工具，但不让 SRT 反向成为新项目的主事实来源。
- 明确 3:4（原黑箱 1080×1440）与 9:16（当前 Harness 默认）的项目级选择，避免无意改变视觉构图。
- 后续可增加按场景/旁白哈希缓存、运行成本记录和长任务子进程树清理。

## 推荐实施顺序

1. 真实 TTS 小样与时间戳验收。
2. 默认黑箱 runner 单场景质量回归。
3. 完整 `advance` 生产链路验收。
4. 本地服务层与 OpenDesign 真实数据接入。
5. 单段 TTS 缓存、旧 SRT 导入和成本优化。

这条顺序把最高风险的外部事实（真实声音和真实视觉生成）提前验证，同时避免在错误协议上继续扩展前端。
